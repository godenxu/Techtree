# 设计说明

记录这张图为什么这么设计，以及几个关键决策的取舍。改动结构之前建议先读一遍。

---

## 一、为什么是《文明》的结构

《文明》的科技树之所以好用，是因为它同时表达了三件事：**时代推进**（横轴）、**分支专精**（纵轴）、**跨线解锁**（连线）。银行科技的演进恰好高度吻合。

| 文明 | 本工具 |
|---|---|
| 时代 Era | 6 个发展阶段：电子化 → 网络化 → 数据化 → 平台化 → 智能化 → 自主进化 |
| 科技分类 | 5A 企业级架构的五条线 |
| 科技节点 | 一项可立项的技术能力，151 个 |
| 前置科技 | 有向无环图，一个节点可有多个前置、可跨线 |
| 解锁的单位/建筑 | `unlocks` 字段：解锁后能做什么业务 |
| 科研点数 | `effort` 投入估算，路线图排程靠它 |
| 已研究 / 可研究 / 锁定 | 建成 / 建设中 / 规划中 / 未启动 |

比文明多出来的关键一点：**规划模式**。选定远期目标后自动反推最小依赖闭包并按年度产能分阶段——这才是规划工具，而不只是一张好看的图。

### 三条依赖规则（保证逻辑不乱）

1. **同线纵向继承**：同分支的后置节点必须依赖至少一个前置，形成连贯脉络。
2. **跨线横向锁**：真正体现「先有数仓才有 CDP」的恰恰是跨线依赖。`实时智能营销决策引擎` 同时锁在数据架构（CDP + 实时数仓）和业务架构（全渠道营销）上，单靠一条线永远解锁不了。全图 255 条边里有 75 条跨 5A 线。
3. **不允许时代倒挂**：节点不能依赖比自己更晚时代的节点，校验器会报错。跨 3 个时代以上的依赖会报警告——多数是合理的长跨度依赖（如 GPU 算力池依赖 Ⅰ 时代的集中存储），确认后可忽略。

## 二、为什么用 5A 而不是自定义分类

5A 企业级架构（业务 / 应用 / 数据 / 技术 / 安全）的最大价值是**和行内架构治理体系说同一套语言**。自己发明一套分类，图挂出去别人第一个问题就是「你这条线对应我们架构文档的哪一章」。

泳道自上而下：**业务 → 应用 → 数据 → 技术**，与架构分层图的阅读习惯一致——越往下越是地基，越往右越是未来。

### 安全架构为什么不是并列泳道

A5 安全架构是**横切关注点**，不是与其他四层并列的第五层。所以：

- 它渲染为底部的**贯穿带**（带红色底纹），而不是普通泳道
- 它指向其他线的依赖画成**红色虚线**，语义是「合规闸门」而非「能力前置」

比如 `分布式核心` 卡在 `统一身份认证 IAM` 上、`大模型基础平台` 卡在 `数据分类分级与脱敏` 上——后者不是技术前置，而是「不做完这个就不许上线」的监管约束。这两类边在图上必须一眼可辨。

## 三、人工智能为什么不单列一条线

这是设计过程中争论最久的一点。结论是：**不单列泳道，但单列视图。**

### 为什么不能塞进数据架构

「AI 的燃料是数据、模型是数据的加工产物」——这在机器学习时代成立，**在大模型时代不成立了**。看一下 AI 实际横跨了什么：

| AI 的组成 | 落在哪条 5A 线 |
|---|---|
| GPU 算力池、推理集群、异构调度 | **A4 技术架构** |
| MLOps、语料工程、向量库、特征平台 | **A3 数据架构** |
| 智能体编排、工具调用、AI 原生应用范式 | **A2 应用架构** |
| AI 客服、智能审批、AI 财富顾问 | **A1 业务架构** |
| 模型风险管理、可解释性、内容安全、对齐 | **A5 安全架构** |

**它横跨全部五条线，塞进任何一条都是降维。** 放在 A3 会让人误以为 AI 是数据部门的事，而实际上算力在基础设施部门、应用形态在研发部门、风险在合规部门。

### 为什么也不能加成第六条泳道

- **破坏 5A 对齐**，前面说的那个价值就打折了
- **跨线连线爆炸**：AI 节点的依赖大量来自其他四条线，独立泳道会让连线密度失控
- **归属打架**：GPU 池到底算技术架构还是 AI 线？一个节点被两条线抢，DAG 结构就烂了

### 最终方案：与安全架构同构处理

安全架构已经因为横切性质被做成贯穿带了，**AI 是同一类东西**，用同一套机制处理，逻辑自洽：

1. **结构维度保持 5A 不动**，每个技术节点严格单一归属，DAG 干净
2. **增加正交的标签维度**：GPU 池仍归 A4 但打 `ai` 标签，MLOps 仍归 A3 但打 `ai`，AI 治理仍归 A5 但打 `ai`
3. **AI 专题视图**：顶栏「专题」切到 AI 视图，一键把所有 `ai` 节点抽出来按依赖重组为独立的人工智能技术树——这就是汇报 AI 专题时用的那张图
4. **领域层视觉特殊处理**：`人工智能与大模型` 这个 L0 节点在领域视图中带一条**贯穿全部泳道的高亮带**，直接表达它的横切性质

同一套标签机制已经复用给信创、风控、开放银行、实时化四个专题。**一份数据，多种切法**，不用重复维护。

## 四、三层颗粒度与自动推导

| 层 | 数量 | 给谁看 | 语言风格 |
|---|---|---|---|
| L0 领域 | 12 | 行领导 | 业务管理语言 |
| L1 能力 | 35 | 科技条线领导 / 规划部门 | 能力语言 |
| L2 技术 | 151 | 架构师 / 项目经理 | 技术语言 |

### 核心机制：上层全部是算出来的

> **依赖关系只在 L2 定义一次。L1 和 L0 的连线由系统自动聚合生成。**

规则：若存在 L2 边 `a→b`，且 `a` 与 `b` 属于不同的可见上层单元 A、B，则生成边 `A→B`，**线宽 = 底层实际边的条数**。视觉上主干依赖自然变粗——领导一眼看到「数据基础与治理」到「人工智能与大模型」之间是最粗的一条主动脉。

进度同理向上聚合：L1 完成度 = 子节点按状态权重加权（已建成 100% / 建设中 50% / 规划中 15%），L0 再聚合一层。

**这样做的意义**：不可能出现「细节改了但汇报图没同步」——因为汇报图根本不是独立维护的，它是算出来的。这同时解决了可维护性问题。

### 混合展开

不是只有三个固定档位。双击任一大节点可以**原地展开它一个**，其余保持折叠——汇报时「我们重点看数据这一块」是最常用的模式。边的聚合逻辑天然支持这种混合状态，因为它是按「每个技术节点当前的可见祖先」实时计算的。

### 背景怎么区分时代与泳道

两个维度必须走**不同的视觉通道**，否则会互相打架，也会盖过节点本身的语义着色（节点颜色编码的是状态 / 成熟度，那是主角）。

- **泳道走色相**：每条 5A 线用自己的主色做**极淡**底色（alpha 0.045），身份主要靠最左侧的彩色轨道条和冻结列的色标表达。底色刻意压得很淡，否则泳道会盖住时代背景，也会和节点的语义着色抢注意力。
- **时代走明度 + 彩虹色带**：时代是主背景层，**画在泳道之上**。列底色按时代顺序做明度递进（暗色主题越往后越亮，亮色主题越往后越深），天然表达"时代推进"；列顶加一条 4px 彩虹色带（靛 → 青 → 绿 → 琥珀 → 紫 → 品红），列间分隔线取同色；列底再压一个巨大的罗马数字水印，缩到全景时也能一眼定位时代。绘制顺序是：泳道底色 → 时代底色 → 泳道分隔线，三层各司其职互不遮挡。

色相与明度分工之后，两套划分可以同时读：横向看色带找时代，纵向看轨道条找架构线。

所有背景颜色都用**行内属性**而不是 CSS class 写进 SVG，这样导出 PNG 时不依赖外部样式表，图片和屏幕上完全一致。

### 为什么同一时代里也要分子列

X 轴是**时代（日历时间）**，不是依赖深度。所以完全可能出现两项技术处在同一个时代、彼此之间却有依赖——比如 `手机银行 APP`（约 2013）和 `智能柜台 / STM`（约 2015）同属数据化时代，后者依赖前者。

早期版本把它们放在同一列的同一个 x 上，那条依赖只能画成向下绕行的回环，很难看也很难读。现在的做法是：**在每个时代列内部，按依赖深度再分子列**，让同代依赖也能左→右流动。

实现上有两个坑：

1. **聚合视图的边会成环**。领域 A 的某些技术依赖领域 B，同时 B 的另一些技术又依赖 A——这在领域层超过七成的边上都成立，强行排序既排不出来，还会把「一屏看全貌」的领域视图拉宽三倍。所以**深度排序只在技术层生效**，聚合层的交叉交给悬停溯源去消解。
2. **防死循环**。即使只排技术层，代码也用有界松弛加贪心破环，而不是朴素拓扑排序——数据出错时宁可排得不完美，也不能把页面卡死。

效果：技术层 255 条依赖边里，只剩 1 条是回环。代价是画布变宽（约 5300×1800），需要横向滚动——这符合科技树的常态，《文明》的科技树本来也是横着拖的。

### 技术生命周期：成熟不等于还该投入

成熟度回答「这项技术靠不靠谱」，**生命周期回答「它是不是已经被时代淘汰了」**。两者正交——集中式核心银行系统就是典型的「成熟期 + 退役中」。

三档：`active` 演进中 / `legacy` 存量维持（仍在跑但不再投入新建）/ `sunset` 退役中（已有明确替代路径，行业正在主动下线）。带 `supersededBy` 指向替代技术，详情面板里可以直接跳过去。

**为什么不直接置灰**：置灰在建设状态维度里已经表示「未建成」，语义会打架——一项已建成、跑得好好的、但正在退役的系统，置灰会被误读成没建。所以退役用**斜纹叠加 + 角标**表达，这样在任何着色维度下都能看见，同时新增了「技术生命周期」着色维度做专项查看。

当前标了 5 项退役中、11 项存量维持，主要集中在第 Ⅰ–Ⅲ 时代。在领域视图里，只有过半子节点已退役的格子才打斜纹，否则整个早期时代会糊成一片。

### 单击与双击怎么分工

双击必然先触发一次单击，所以「单击看详情 + 双击下钻」是天然打架的设计——想下钻就必然先弹出详情框，还会挡住展开后的内容。

现在按**节点类型**把手势分开，两者永不落在同一个对象上：

| 对象 | 单击 | 双击 |
|---|---|---|
| 聚合格（领域 / 能力） | **下钻展开** | 收拢一级 |
| 聚合格右上角的 ⓘ | **看详情** | — |
| 技术节点 | **看详情**（它本来就没有下钻） | 收拢一级 |

聚合格的详情移到一个显式的 ⓘ 热区上，既消除了冲突，也让「这里可以看详情」变得可见。

### 展开与收拢的动效

关键不是「出现和消失」，而是让人看清**一个格子变成了三个**。所以：

- 展开时，新出现的子格从**父格的旧位置**放大出来（translate + scale 0.42 → 1）
- 收拢时，即将消失的子格被克隆成幽灵层，**收回接管它的父格的新位置**再淡出
- 位置发生变化的既有格子走 FLIP：先按旧位置反向位移，再动画归零

### 聚合节点按「主体 × 时代」切分

最初的做法是一个领域只占一个格子，位置取它覆盖技术的时代中位数。这是个错误设计：**所有 12 个领域的中位数都落在第 Ⅲ–Ⅴ 时代，于是电子化、网络化和自主进化这三个时代整列消失了**——拿这张图讲演进路径，开头和结尾直接断代，说不通。

根因是一个领域天然横跨多个时代：「渠道与客户触达」从 Ⅰ 时代的柜面系统一直到 Ⅴ 时代的数字人。把它压成一个格子必然丢信息。

现在聚合单元的 ID 形如 `D06@E4`（领域 × 时代）或 `C601@E4`（能力 × 时代）：**一个领域在它有技术节点的每个时代各出现一格**。于是：

- 六个时代在任何粒度下都始终存在，演进故事完整
- 领域视图变成一张 12 行 × 6 列的矩阵，每格显示该领域在该时代的技术数与完成度，很适合投影汇报
- 每格的连线依然由底层技术边自动聚合，规则不变
- 演示模式随之有了意义：逐幕点亮各时代那一列的新增格子

代价是领域视图的格子从 12 个变成约 54 个。实测下来这反而更有信息量——领导看到的是「这个领域从哪个时代开始建、现在建到哪」，而不是一个孤零零的进度环。

## 五、数据可信度：为什么没有百分比

设计初期字段里有 `adoption: 92%` 这样的普及率。后来删掉了，原因是：

**「某家行某项技术建到什么程度」这件事，公开信息严重不足。** 银行年报通常只披露科技投入总额和少数亮点项目，内部建设进度不对外。在一张要拿去做规划决策的图上，伪精确的百分比比不给数字更有害。

改成三件事：

1. **分档代替百分比**：普遍具备 / 多数在建或已建 / 领先机构具备 / 个别试点 / 尚无规模落地。分档是判断，百分比是数据，不能混。
2. **每个节点带 `confidence` 置信度**，低置信度在界面上标灰并提示「待核实」。
3. **`evidence` 证据层**：详情面板底部固定有「判断依据」区，有证据的列证据和来源链接，没有的明确写「基于通用行业认知，未经核实」。

技术本身的**成熟度**判断（K8s 是成熟期、智能体编排是早期采用）属行业共识，可信度高，这部分保留。

### 金融科技发展奖作为证据源

人民银行金融科技发展奖是金融业唯一部级科技类奖项，**有年份、有单位、有项目名、有等级、官方公示可核查**，正好补上上面的缺口。用法：

- 节点角标 🏆，悬停显示关联的获奖项目数
- 单位视图下可作为「已建成且有一定成熟度」的证据并附来源链接
- 年度 × 领域**热力图**，看这些年行业投入热点的迁移轨迹

两条限制写进了界面：**获奖代表有成熟度，未获奖不代表没建设**。徽章只做加分项，绝不用作「未获奖 = 未建成」的反向推断。

## 六、技术实现的两个约束

### 为什么不用 fetch 读 JSON

`file://` 协议下浏览器的 CORS 策略会拦掉 `fetch()` 读本地文件，页面直接白屏，必须起本地 HTTP 服务才能跑——在行内电脑上这恰恰是最麻烦的一步。

所以数据文件写成 `.js`（`TT.nodes = [...]` 形式）用 `<script src>` 加载。**classic script 不受 CORS 限制**，双击照样能开。代价是数据文件需要一层薄薄的 JS 包装，换来的是零前提条件打开。

同理，代码用普通 `<script>` 而非 ES module——`type="module"` 同样受 CORS 约束。

### 为什么不用力导向布局

银行科技树需要**稳定可预期的版面**：每次打开位置一致，截图进 PPT 后下次还能对上。所以用确定性网格布局：X 轴按时代分列，Y 轴按 5A 分泳道，同格内按领域聚拢后纵向堆叠，拥挤的列自动分裂为子列以控制画布高宽比。

代价是连线交叉比力导向图多一些，这由悬停溯源（上游金色、下游青色、其余淡出）来补偿——实际使用中，人看的从来不是全图连线，而是某一个节点的那条链。
